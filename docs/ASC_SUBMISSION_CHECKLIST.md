## 1. App Review Information → Notes

**Where:** ASC → your app → the 1.0 version (do it for **iOS and macOS
separately**; they are different records) → *App Review Information* → *Notes*.

**Why this is first:** it is minutes of work and it prevents the most likely
rejection. FlatFold is end-to-end encrypted, so the server holds no message
history. A reviewer who signs into one account sees an **empty conversation
list** — which is indistinguishable from a broken app. Nothing else in the
submission explains that.

The demo-account fields hold **one** account. The second account, and the
explanation, have nowhere to live except this box.

```
FlatFold is an end-to-end encrypted messenger. Two demo accounts are provided
because a single account cannot demonstrate a conversation.

WHY: messages are encrypted on the sending device and decrypted only on the
receiving one. The server never holds readable content, and it deletes the
ciphertext as soon as it is delivered. There is therefore no server-side history
to pre-load into an account. Signing into one account alone shows an empty
conversation list — that is the product working correctly, not a failure.

ACCOUNTS (both use the password in the Demo Account field above):
  1. flatfold_review1
  2. flatfold_review2

TO SEE A CONVERSATION:
  1. Sign in as flatfold_review1. You will be asked for the password twice —
     once to sign in, once to unlock the on-device encrypted keystore. This is
     deliberate: the key that decrypts local data is derived from the password
     and is never stored, so it must be re-derived. Unlocking takes a second or
     two (Argon2id).
  2. Go to Contacts, add "flatfold_review2", and send a message.
  3. Sign out, sign in as flatfold_review2 (same password), and you will see the
     message. Reply to it.
  4. Sign back in as flatfold_review1 to see the exchange from the other side.

     Note: signing out clears the local decrypted store, so account 1's history
     will not survive the switch. Two devices (or a device plus the web app at
     https://flatfold.ponderance.dev) shows the conversation live on both sides
     and is the fastest way to review it.

THINGS THAT MAY LOOK WRONG AND ARE NOT:
  - No email or phone number is collected. A username and password is the whole
    identity. This is the product's purpose, not a missing step.
  - The app asks for the password again after a reload or relaunch. The
    decryption key lives only in memory, by design.
  - Notifications never contain message text or a sender name. They say "New
    activity". The server cannot read the message, so it cannot put it in a
    push payload.
  - Settings → About → "What the server stores" lists, in plain language, every
    single column the server holds. It is complete and kept in sync with the
    database schema by an automated test.

CONTACT: anmol@ponderance.dev — happy to walk through anything.
```

**Also fill:** *Contact Information* (first/last name, phone, email) — already
populated. *Demo Account* name and password — already populated with account 1.

## 3. Which build goes to which platform

**The short answer: the app tells you.** Every build stamps the git commit into
the bundle (`vite.config.ts` → `BUILD_ID` = `git rev-parse --short HEAD`, plus a
literal `+` if the working tree was dirty at build time), and it is displayed at
**Settings → About → Build**. So a build is traceable to a commit from inside
the running app, which is exactly the ambiguity you are worried about with many
branches in flight.

**Before you archive:**

```bash
git rev-parse --abbrev-ref HEAD     # the branch you think you're shipping
git rev-parse --short HEAD          # note this: it is what About will show
git status --porcelain              # MUST be empty, or About shows "abc1234+"
```

A `+` in the Build string means the binary contains uncommitted work and is not
reproducible from any commit. Never ship one.

**After the upload, before you attach the build to a version:** install it from
TestFlight, open **Settings → About**, and confirm the Build string matches the
SHA you noted and has no `+`. That is the only check that proves the binary
carries the code you meant — the ASC build number (`1`, `2`, `3`) is just a
counter and says nothing about provenance.

**Platform is not ambiguous, and you cannot cross them by mistake.** ASC derives
it from the binary: an iOS archive can only attach to the iOS version record, a
Mac Catalyst archive only to the macOS one. They appear in separate Builds lists
under each platform. What you *can* get wrong is uploading the right platform
from the wrong branch — which is what the Build string above is for.

**Build numbers must strictly increase** per platform, or the upload is
rejected. The fastlane `beta` lane already handles this
(`latest_testflight_build_number + 1`, injected at archive time, never mutating
the committed project file).

## 4. App Privacy — but upload build 3 FIRST

**Ordering matters and is easy to get backwards.** `PrivacyInfo.xcprivacy` is
**bundled into the binary**. It now declares the push token, but the only builds
on ASC are 1 and 2, both older than that change. Filling in the label today
would describe a build that does not declare it.

> **manifest (done) → build 3 uploaded → then the label.**

**Where:** ASC → App Privacy → *Edit*.

| Question | Answer |
| --- | --- |
| Do you or your third-party partners collect data from this app? | **Yes** |
| Data types → **Identifiers → User ID** | Collected. **Linked** to the user. Purpose: **App Functionality** only. **Not** used for tracking. |
| Data types → **Identifiers → Device ID** | Collected. **Linked** to the user. Purpose: **App Functionality** only. **Not** used for tracking. |
| Everything else | **Not collected** |
| Is data used for tracking? | **No** |
| Third-party partners | **None** (there are no SDKs) |

*User ID* is the username. *Device ID* is the APNs / web-push token, which
`apns_subscriptions` genuinely stores against a username so a notification can be
routed.

**The one answer that needs your explicit sign-off:** declaring message content,
photos, audio and contacts as **not collected**. Apple defines collection as
transmitting data off-device *in a way that allows you to access it*. End-to-end
encryption means you cannot access it, so it is not collected — the same
position Signal and WhatsApp take, and the same reasoning covers the encrypted
recovery blob and queued ciphertext. It is honest and well-supported, but it is
an affirmative claim about an encrypted messenger, which is the category Apple
scrutinises. Make it knowingly.

## 6. Custom EULA (License Agreement)

**Where:** ASC → *App Information* → *License Agreement* → *Custom*.

**Why custom rather than Apple's standard one:** FlatFold is AGPL-3.0, and
GPL-family licences forbid imposing further restrictions. Apple's standard EULA
imposes some (device limits, DRM). That conflict is what got VLC pulled from the
App Store in 2011. `LICENSE` now carries an AGPL §7 additional permission that
resolves it for Apple's channels — the EULA below is the other half.

### The authoritative source, which you must copy from

Apple publishes the required clauses here — **both links verified live
2026-07-28 (HTTP 200):**

- **Minimum Terms:** <https://www.apple.com/legal/internet-services/itunes/dev/minterms/>
- Standard EULA (for reference): <https://www.apple.com/legal/internet-services/itunes/dev/stdeula/>

**Copy Apple's clause text verbatim from that first page.** I deliberately have
not reproduced it here: Apple revises it, a stale copy in a repo is worse than
no copy, and paraphrasing the minimum terms is the single most common reason a
custom agreement is rejected. Paste the FlatFold preamble below, then Apple's
ten clauses under it.

### Then Apple's ten required clauses, in this order

Paste them verbatim from the Minimum Terms page. Use this as a checklist that
none is missing — an agreement is rejected for an omitted clause:

1. **Acknowledgement** — the agreement is between you and the developer, not Apple; the developer alone is responsible for the app and its content.
2. **Scope of License** — non-transferable licence to use the app on Apple-branded products you own or control, as permitted by the App Store Terms of Service.
3. **Maintenance and Support** — the developer is solely responsible; Apple has no obligation whatsoever.
4. **Warranty** — the developer is responsible for any warranties; on failure, Apple may refund the purchase price, and beyond that has no obligation.
5. **Product Claims** — the developer, not Apple, addresses claims about the app (liability, legal/regulatory compliance, product-liability, consumer protection, privacy).
6. **Intellectual Property Rights** — the developer, not Apple, is responsible for any third-party IP infringement claim.
7. **Legal Compliance** — the end user represents they are not in a U.S.-embargoed country and are not on a prohibited-parties list.
8. **Developer Name and Address** — name and contact for end-user questions, complaints and claims.
9. **Third Party Terms of Agreement** — the end user must comply with applicable third-party terms.
10. **Third Party Beneficiary** — Apple and its subsidiaries are third-party beneficiaries and may enforce the agreement against the end user.

**One thing to get right in clause 8:** the name and address must match the
declarant on file elsewhere (the Apple Developer account, and the ANSSI
declaration). If FlatFold ever moves to an LLC, all three change together.

## 7. Where the screenshots actually stand

Honest status, because "screenshots: done" would be wrong.

**Working:** `scripts/screenshots.sh` drives a simulator, captures at exact
device pixel sizes, asserts the size afterwards, cleans the status bar to 9:41
with full battery and signal, and waits on the app's own settled signal so a
capture never races the render.

**Captured so far:** the login screen and the transparency page, on iPhone and
iPad. Both are real, correctly sized, and honest — but as marketing they are
thin, and you were right to say so. The transparency page is genuinely the
strongest single claim in the submission; the login screen is filler.

**What is missing and why:** chat, contacts and settings all need a
**logged-in** state with a **populated conversation**, and there is no shortcut
to one. Two facts collide:

1. A fresh install has no session. My credential guess for a login was wrong —
   measured, not assumed: the web app returned **`401 /api/auth/login`**, which
   also corrects an earlier claim. `STATUS.md` says the simulator "cannot reach
   a logged-in state" because of Argon2/HPKE WASM; the app in fact launches,
   renders and stays alive there — what failed was the credential, not the
   runtime.
2. Even with a correct login, **history is on-device only**. Signing a real
   account into a fresh simulator shows an empty app, for the same reason the
   review notes in §1 exist.

**So the right fix is to seed a conversation rather than to borrow one** — sign
up two throwaway accounts, exchange scripted messages, and screenshot that. That
also keeps real private conversations out of an App Store listing, which is
worth having as a rule regardless.

The Mac screenshots have a separate blocker: a default-sized Catalyst window
renders the **phone** tab bar (`chatChrome.ts` takes the narrow branch), so a
2880×1800 capture would show a Mac app wearing phone chrome. The wide layout has
to be fixed before Mac shots are worth taking.
